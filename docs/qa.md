# Testing the platform

Off by default (`qa.enabled: false`). With it on, the agent tests the whole platform in a headless browser by your instructions and writes a report per run. Nothing goes through the issue tracker: no ticket, no comment; what to do about a finding is yours to decide.

**The instructions.** One file, `qa.instructions` (default `~/arceus/data/qa/instructions.md`, next to the secrets): the platform's URL, its test accounts and what to test, in any shape. The `runner` phase copies [qa-instructions.example.md](../config/qa-instructions.example.md) there once and never overwrites it. The example is all HTML comments, which the agent never gets, so until you write the instructions the file counts as empty: `arceus-runner check` fails on it with `qa` on, and a run reports it had no instructions. The runner adds how to work and how to report. A run keeps the text it started with, so editing the file never changes a run under way.

**Starting a run.** `arceus-runner qa run` queues one and prints its number; `qa status` lists the latest runs; `qa stop [n]` stops a queued or running one (its report keeps what it found). With `qa.schedule` (`{days: [mon, …], at: "02:00"}`, in `schedule.timezone`) the runner queues runs by itself. A scheduled time is queued once, also across restarts; one missed by more than an hour is not made up, and one that comes while a run is queued or under way is skipped.

**How it runs.** A run is the Bulava task `qa-<n>`. It holds the shared workspace from start to end, and a queued run goes before new tickets. Every repository is put on a local branch `arceus-qa/<n>` at its default branch as last fetched, so the agent can name the file and line it suspects; it changes no code. A repository with uncommitted work (a ticket waiting on people) is left as it is and read with `git show`. Afterwards every repository goes back where it was. Past `qa.timeout` (8 h) the run is stopped and reported as unfinished.

**The report.** The agent writes `findings.json` and its screenshots; the runner validates them and writes `report.html` under `qa.reports`: what was checked, and each problem with its steps, the screenshot where it went wrong, expected against actual, how often, and the suspected cause linked to the code at the commit read. The outcome is one of:

- no problems found: the run finished, the report was read whole, and at least one thing was checked with nothing left unchecked or skipped;
- no problems in what was checked, with what could not be checked or was skipped listed;
- could not test (the site down, the login refused);
- did not finish: nothing checked, everything skipped, a problem without a description, a report the runner could not read, or a run the engine ended any other way than finished; the report and Slack say why.

Bulava has Codex review the agent's report before the run ends. A test run is sent with a review of its own (engine/SERVER.md, "Review budget of a task"): at most three rounds, judged by the runner's criteria for a test report (each finding backed by its steps and screenshot, a summary that claims no more than the checks show, numbers that agree) in place of the server's rule for data changes, since test data on a test stand is expected and naming it is enough. The agent is given the same criteria in its brief. Codex reads `findings.json` itself, as it is at each round: the engine reads a report only from `artifacts/` of the workspace and only as html, md or txt, so the runner links `artifacts/qa-<n>/findings.txt` to the agent's file, the agent names that link in its closing summary, and the links go when the run is over. The engine reads at most 60 000 characters of one file, so a longer report comes in parts (`findings.json`, `findings-2.json`, …, each under 40 KB), and `findings.json` then says how many parts, checks and findings there are in all; the runner checks those totals, and that the numbering has no gap. The parts are reviewed one per attempt of the task, three rounds each: once the engine ends an attempt `done`, the runner links the next part and asks the agent to finish again naming it. The report is published from all the parts together, with the objections left on each part under its name; a part the review never reached (the run stopped, ran out of time, or the engine did not take the next attempt), one added after the parts were counted, or one changed after its review, is shown as not reviewed, and the run counts as one whose report did not pass its closing review. A part larger than the engine reads is a problem of the report. The engine keeps them with the task, so a run taken up again after a crash is reviewed the same way. A report Codex still objects to after the third round is accepted with its notes: the task ends `done`, nothing was committed, and the runner keeps the run's findings while the report, the console's list and Slack all say the report did not pass that review, with the objections Codex left unsettled shown in the report. A run sent to an older engine, which ends such a run `failed`, `needs-user`, is read the same way. The run's outcome still has to come from the report itself: one that names no check that was done (none `ok` or `problem`), or that the runner could not read whole, did not finish, findings or not. One that found no problems is never "no problems found", only "no problems found, but the report did not pass its closing review". Any other `needs-user` (an answer from Codex with no readable verdict, a review that passed but left something for a person, a commit) is still a run that did not finish. With `qa.enabled`, live mode needs an engine that takes this review (`dispatch.sh --report-criteria`, Bulava 1.20); `arceus-runner probe-bulava` shows whether it does.

**How much a report keeps.** One run keeps at most `qa.max_checks` (1000) entries of what was checked, `qa.max_findings` (300) findings, `qa.max_files` (1000) screenshots and recordings, `qa.max_media_mb` (1024) MB of them together, and a `findings.json` of `qa.max_report_mb` (8) MB. The limits guard the report page and the disk against an agent that runs away; they say nothing about how much the agent can test well, so raise them when the instructions are long. The agent is told them, and to list every check it was asked for, one entry each, the ones it did not get to as skipped. Whatever goes past a limit is left out, and the report lists it by count and by name, so such a run is never "no problems found". The instructions themselves are capped at 64 KiB (the brief goes to the agent as one command-line argument): split a larger test plan into several runs, one after another, since a run reads the instructions when it starts, not when it is queued.

With the web console on, the reports are its **Test runs** ([console.md](console.md)): people with the QA role (or admins) start and stop runs there and edit the instructions, and everyone signed in reads the reports. Without it, reports are served on `127.0.0.1:3300` (`qa.port`): `ssh -L 3300:127.0.0.1:3300 <user>@<vm>`, then `http://localhost:3300/`. Either way the list is read from the database on every visit, so queued and running runs show at once, and only reports and their screenshots are served, never the instructions.

**Slack and Grafana.** The channel hears when a run starts (and whether the schedule started it) and how it ended, with the agent's two or three lines and the report's link. On **Arceus · now** the agent shows as Testing, and the run is listed as `qa-<n>`.
